Вы создали нечто, что работает на вашем компьютере — скрипт для конвертации изображений, функцию для выполнения вычислений, небольшую программу, выполняющую полезную задачу. В какой-то момент вы захотите выйти за пределы своего ноутбука: разместить это на сайте, чтобы посетители могли пользоваться сервисом, отправить ссылку другу или коллеге, или оформить в нечто, за что можно взимать плату. Как только вы хотите, чтобы другие могли вызывать ваш код откуда угодно — из браузера, мобильного приложения, другого сервера — вам нужно предоставить его как API.

API (Application Programming Interface) превращает ваш код в сервис со стабильным URL. Вместо того чтобы делиться скриптом и просить людей настраивать собственное окружение для его запуска, вы запускаете его один раз, а они им пользуются. Именно это и строит данное руководство.

По завершении этого руководства у вас будет контейнеризованный API, работающий на GCP, доступный по публичному HTTPS URL и разворачиваемый одной командой. Логика API — на ваше усмотрение; это руководство охватывает всё остальное: настройку Docker, Artifact Registry, конфигурацию Cloud Run, переменные окружения, публичный доступ и верификацию после развёртывания.

Примеры используют Python (FastAPI + uvicorn), но шаги на стороне GCP применимы к любому языку или фреймворку, который может работать в контейнере.

## Как всё это устроено

Прежде чем прикасаться к инструментам, вот полная картина того, что вы создаёте:

```
Local Machine                         GCP
──────────────────────────────────────────────────────────
                                      ┌───────────────────┐
1. Write Dockerfile                   │  Artifact         │
2. docker build ──────── docker push ▶│  Registry         │
3. docker run   (local test)          │  (image storage)  │
                                      └─────────┬─────────┘
                                                │ pull image
                                                ▼
                                      ┌───────────────────┐
                                      │   Cloud Run       │
                                      │   (managed        │
                                      │    runtime)       │
                                      └─────────┬─────────┘
                                                │
                                                ▼
                                      https://your-service-xxxx.run.app
                                      (public HTTPS API endpoint)
```

**Artifact Registry** хранит ваши Docker-образы — это приватный реестр образов внутри вашего проекта GCP. **Cloud Run** — управляемая среда выполнения контейнеров, которая загружает ваш образ, запускает его, автоматически обрабатывает терминацию HTTPS и масштабирование, а также предоставляет стабильный URL.

Всё остальное — Cloud Build, Cloud Storage, GKE — является опциональным. Минимально работоспособная установка требует только этих двух сервисов.

## Настройка проекта GCP

Прежде всего вам понадобится проект GCP. Проект является контейнером для всех ваших ресурсов GCP — биллинг, API, IAM-разрешения и сервисы привязаны к проекту.

### Установка и аутентификация gcloud CLI

Установите [Google Cloud CLI](https://cloud.google.com/sdk/docs/install), затем выполните аутентификацию:

```bash
gcloud auth login
gcloud config set project YOUR_PROJECT_ID
```

Аутентифицируйте Docker для работы с Artifact Registry (один раз на каждом компьютере):

```bash
gcloud auth configure-docker us-central1-docker.pkg.dev
```

Эта команда записывает вспомогательный модуль учётных данных в `~/.docker/config.json`. Её нужно выполнить только один раз — настройка сохраняется между сессиями терминала.

### Создание проекта

Перейдите в [Google Cloud Console](https://console.cloud.google.com), щёлкните на селектор проектов вверху, затем выберите **New Project**. Задайте имя и запишите Project ID — он потребуется в каждой CLI-команде ниже.

Или через CLI:

```bash
gcloud projects create YOUR_PROJECT_ID --name="My API Project"
gcloud config set project YOUR_PROJECT_ID
```

### Подключение биллинга

Cloud Run и Artifact Registry требуют, чтобы к проекту был привязан биллинговый аккаунт, прежде чем их можно будет использовать — даже если ваш объём использования остаётся в пределах бесплатного уровня. GCP использует биллинговый аккаунт для определения ответственного за расходы, а не для немедленного списания средств.

В Console: **Billing** → **Link a billing account** → выберите или создайте биллинговый аккаунт.

### Включение необходимых API

Сервисы GCP по умолчанию отключены. Включите два сервиса, используемых в этом руководстве:

```bash
gcloud services enable artifactregistry.googleapis.com run.googleapis.com
```

Это занимает около 30 секунд и выполняется один раз для каждого проекта.

### IAM-разрешения

Если вы являетесь владельцем проекта — аккаунтом, создавшим проект — у вас уже есть полные разрешения, и этот раздел можно пропустить.

Если вы развёртываете из CI/CD-конвейера или хотите следовать принципу наименьших привилегий, создайте выделенный сервисный аккаунт только с необходимыми ролями:

| Роль | Что разрешает |
|------|---------------|
| `roles/artifactregistry.writer` | Отправка образов в Artifact Registry |
| `roles/run.developer` | Развёртывание и управление сервисами Cloud Run |

```bash
gcloud iam service-accounts create api-deployer \
  --display-name="API Deployer"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:api-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/artifactregistry.writer"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:api-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/run.developer"
```

Для личного использования со своего компьютера достаточно вашего пользовательского аккаунта с правами владельца — сервисный аккаунт не нужен.

## Предварительные требования: настройка Docker

### Что такое Docker и зачем он нужен?

Docker — это платформа контейнеризации. **Контейнер** упаковывает код вашего приложения вместе с его средой выполнения, зависимостями и конфигурацией в единый переносимый блок, который работает одинаково везде.

Без контейнеризации развёртывание кода на удалённом сервере означает необходимость убедиться, что на сервере установлена точно такая же версия Python, точно такие же пакеты из `requirements.txt`, те же переменные окружения и та же структура каталогов, что и на вашем ноутбуке. Это хрупко — незначительные различия между локальным и производственным окружениями вызывают трудновоспроизводимые и ещё более трудно диагностируемые ошибки.

Контейнер устраняет этот класс проблем. Вы один раз описываете окружение в **Dockerfile**, собираете его в **образ**, и этот образ работает одинаково на вашем ноутбуке, на GCP или на любом компьютере с Docker.

**Два термина, которые вы будете встречать на протяжении всего руководства:**

- **Образ (Image)** — доступный только для чтения шаблон, описывающий файловую систему и команду запуска. После сборки неизменяем. Можно представить его как снимок.
- **Контейнер (Container)** — запущенный экземпляр образа. Когда Cloud Run получает запрос, он запускает контейнер из вашего образа для его обработки. По завершении запроса контейнер может быть оставлен в горячем состоянии для следующего запроса или остановлен.

Вы собираете образ локально, отправляете его в Artifact Registry (хранилище образов на GCP), а Cloud Run загружает и запускает его оттуда.

### Установка Docker Desktop

Загрузите и установите Docker Desktop с [docker.com](https://www.docker.com/products/docker-desktop/). После установки запустите Docker Desktop и дождитесь, пока значок кита в строке меню перестанет анимироваться — это означает, что демон запущен.

Проверьте установку:

```bash
docker --version
# Docker version 27.x.x, build ...

docker info
# Should print system info without errors
# If you see "Cannot connect to the Docker daemon" — Docker Desktop is not running
```

## Два сервиса, которые вам нужны

GCP имеет обширный каталог сервисов. Для этого руководства вам нужны ровно два из них.

**Artifact Registry** хранит ваши Docker-образы. Представьте его как приватный Docker Hub, находящийся внутри вашего проекта GCP. Cloud Run загружает образы отсюда во время развёртывания.

**Cloud Run** — управляемая среда выполнения контейнеров. Она обрабатывает терминацию HTTPS, автомасштабирование, проверки работоспособности и откаты развёртывания. Вы предоставляете образ и набор параметров; сервис запускает ваш контейнер и предоставляет его по стабильному URL.

---

## Бесплатный уровень и лимиты использования

Оба сервиса имеют постоянные бесплатные уровни — не просто пробные кредиты.

| Сервис | Бесплатный уровень | Выше бесплатного уровня |
|---------|-----------|-----------------|
| Artifact Registry | 0,5 ГБ хранилища/месяц | $0,10/ГБ/месяц |
| Cloud Run | 2 млн запросов/месяц | $0,40 за миллион запросов |
| Cloud Run | 360 000 ГБ-секунд памяти/месяц | $0,00000250/ГБ-секунду |
| Cloud Run | 180 000 vCPU-секунд/месяц | $0,00001000/vCPU-секунду |
| Cloud Run | 1 ГБ исходящего трафика (Северная Америка)/месяц | $0,12/ГБ |

Для API с низким и средним трафиком (десятки тысяч запросов в месяц) вы, скорее всего, останетесь в пределах бесплатного уровня Cloud Run. Расходы на Artifact Registry зависят от количества хранимых версий образов — см. раздел о политике очистки ниже.

## Единовременная настройка: Artifact Registry

Перед любым развёртыванием вам нужен репозиторий внутри Artifact Registry для хранения образов. Выполните это один раз для каждого проекта:

```bash
gcloud artifacts repositories create my-service \
  --repository-format=docker \
  --location=us-central1 \
  --project=YOUR_PROJECT_ID \
  --description="Container images for my-service"
```

После этого имя вашего образа будет следовать такому шаблону:

```
us-central1-docker.pkg.dev/YOUR_PROJECT_ID/my-service/my-service:latest
```

### Политика очистки

Artifact Registry взимает плату за хранение. Без политики очистки старые слои образов накапливаются незаметно. Примените политику, которая сохраняет три последние версии и удаляет всё старше 30 дней:

```bash
gcloud artifacts repositories set-cleanup-policies my-service \
  --location=us-central1 \
  --project=YOUR_PROJECT_ID \
  --policy=cleanup-policy.json \
  --no-dry-run
```

`cleanup-policy.json`:

```json
[
  {
    "name": "keep-latest-3",
    "action": {"type": "Keep"},
    "mostRecentVersions": {"keepCount": 3}
  },
  {
    "name": "delete-old",
    "action": {"type": "Delete"},
    "condition": {"olderThan": "30d"}
  }
]
```

Флаг `--no-dry-run` обязателен — без него политика оценивается, но не применяется.

## Определение эндпоинтов API

Cloud Run запускает ваш контейнер и не имеет сведений о том, что делает ваше приложение. Ваше приложение определяет маршруты, а Cloud Run открывает их через URL сервиса.

После развёртывания каждый определённый вами эндпоинт доступен по адресу:

```
https://{your-service-url}/{endpoint-path}
```

Например, если URL вашего сервиса Cloud Run — `https://my-service-abc123-uc.a.run.app` и вы определяете маршрут `/convert`, он будет доступен по адресу `https://my-service-abc123-uc.a.run.app/convert`.

### Почему эндпоинт проверки работоспособности важен

Эндпоинт проверки работоспособности — это выделенный маршрут, как правило `/health`, — который немедленно возвращает ответ `200 OK` без каких-либо побочных эффектов. Cloud Run использует его для подтверждения корректного запуска контейнера. Инструменты мониторинга используют его для обнаружения сбоев. Ваш скрипт верификации после развёртывания использует его первым после каждого развёртывания.

Без маршрута `/health` единственный способ убедиться, что сервис жив после развёртывания, — вызвать один из реальных эндпоинтов и надеяться на корректное поведение, что является ненадёжной заменой.

### Минимальный пример на Flask

Вот минимальное Flask-приложение с проверкой работоспособности и одним функциональным эндпоинтом:

```python
# app/main.py
from flask import Flask, jsonify, request

app = Flask(__name__)

@app.route("/health")
def health():
    return jsonify({"status": "ok"})

@app.route("/process", methods=["POST"])
def process():
    data = request.get_json()
    result = {"output": f"processed: {data.get('input', '')}"}
    return jsonify(result)
```

`requirements.txt`:

```
flask
gunicorn
```

После развёртывания оба маршрута доступны через URL сервиса:

| Маршрут | Полный URL |
|-------|----------|
| `/health` | `https://your-service-url/health` |
| `/process` | `https://your-service-url/process` |

### Flask и FastAPI в Dockerfile

Выбранный фреймворк влияет на строку `CMD` в вашем Dockerfile. Flask использует **gunicorn** (производственный WSGI-сервер); FastAPI использует **uvicorn**:

```dockerfile
# Flask + gunicorn
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "1", "app.main:app"]

# FastAPI + uvicorn
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

Всё остальное в Dockerfile — базовый образ, порт, рабочий каталог — одинаково независимо от фреймворка.

## Dockerfile

Cloud Run запускает любой контейнер, который слушает порт `8080` и корректно завершает работу по сигналу `SIGTERM`. Минимальный готовый к production Dockerfile для Python API:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

Три вещи, заслуживающие внимания:

- **`python:3.12-slim`** исключает компиляторы, инструменты тестирования и документацию из базового образа. Меньший образ означает более быструю загрузку при развёртывании и более низкие расходы на хранение в Artifact Registry.
- **`--no-cache-dir`** предотвращает запись кэша загрузок pip в слой образа. Кэш никогда не используется повторно внутри работающего контейнера, поэтому это чистые потери.
- **Порт `8080` обязателен.** Cloud Run направляет весь трафик на этот порт. Хост должен быть `0.0.0.0` — не `localhost` и не `127.0.0.1` — иначе проверки работоспособности Cloud Run будут молча завершаться ошибкой.

## Локальное тестирование перед отправкой

Всегда проверяйте, что контейнер работает локально, прежде чем отправлять его на GCP. Сломанный образ, отправленный в Artifact Registry, тратит время и ресурсы хранилища.

Соберите образ:

```bash
docker build --platform linux/amd64 -t my-service:local .
```

Флаг `--platform linux/amd64` критически важен, если вы работаете на Mac с Apple Silicon. Без него Docker соберёт образ `arm64`. Аппаратная платформа Cloud Run — `amd64` — молча отклонит неправильную архитектуру. Флаг принудительно выполняет кросс-платформенную сборку.

Запустите контейнер локально:

```bash
docker run --rm -p 8080:8080 \
  -e API_KEY=your-dev-key \
  my-service:local
```

Флаг `-p 8080:8080` отображает порт 8080 внутри контейнера на порт 8080 на вашем компьютере. Флаг `-e` передаёт переменные окружения.

Проверьте:

```bash
curl http://localhost:8080/health
# Expected: {"status": "ok"}
```

Если проверка работоспособности проходит, контейнер запускается корректно и сервер слушает. Остановите его с помощью `Ctrl+C` перед продолжением.

## Конвейер выпуска

Последовательность сборка → отправка → развёртывание выполняется при каждом выпуске. Разбита на три составных скрипта, чтобы каждый шаг можно было тестировать независимо:

**`scripts/build.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail

IMAGE="us-central1-docker.pkg.dev/YOUR_PROJECT_ID/my-service/my-service:latest"

docker build --platform linux/amd64 -t "$IMAGE" .
```

**`scripts/push.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail

IMAGE="us-central1-docker.pkg.dev/YOUR_PROJECT_ID/my-service/my-service:latest"

gcloud auth configure-docker us-central1-docker.pkg.dev --quiet
docker push "$IMAGE"
```

**`scripts/deploy.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail

gcloud run deploy my-service \
  --image "us-central1-docker.pkg.dev/YOUR_PROJECT_ID/my-service/my-service:latest" \
  --platform managed \
  --region us-central1 \
  --memory 512Mi \
  --cpu 1 \
  --concurrency 1 \
  --max-instances 100 \
  --timeout 60 \
  --allow-unauthenticated \
  --project=YOUR_PROJECT_ID
```

**`scripts/release.sh`** — объединяет все три:

```bash
#!/usr/bin/env bash
set -euo pipefail
bash scripts/build.sh && bash scripts/push.sh && bash scripts/deploy.sh
```

После этого `bash scripts/release.sh` — единственная команда, необходимая для выпуска новой версии.

## Конфигурация Cloud Run: объяснение каждого параметра

| Параметр | Значение | Обоснование |
|-----------|-------|-----------|
| `--memory` | `512Mi` | Большинство API для обработки изображений и вычислений укладываются в 512 MiB. Метрики Cloud Run покажут, если потребуется больше. |
| `--cpu` | `1` | Один vCPU на экземпляр. CPU выделяется только во время обработки запроса — без простойного биллинга. |
| `--concurrency` | `1` | Каждый экземпляр обрабатывает один запрос за раз. Правильно для CPU-нагруженных задач, где параллельные запросы конкурировали бы за CPU и снижали производительность обоих. Для I/O-нагруженных сервисов повысьте до 10–80. |
| `--max-instances` | `100` | Ограничивает количество одновременных экземпляров. Предотвращает неконтролируемое масштабирование при всплеске трафика или атаке. Устанавливайте исходя из допустимых максимальных расходов, а не ожидаемого трафика. |
| `--timeout` | `60` | Таймаут запроса в секундах. Cloud Run завершает запрос и возвращает 504, если обработка превышает это значение. Устанавливайте с учётом самой медленной ожидаемой операции с запасом. |
| `--allow-unauthenticated` | — | Делает URL публично доступным. См. следующий раздел об оговорке IAM. |

**Что означает `--concurrency 1` на практике.** При concurrency равном 1 каждый активный запрос получает свой экземпляр. Если два запроса поступают одновременно, Cloud Run запускает второй экземпляр вместо постановки второго запроса в очередь. Для CPU-нагруженных задач — обработки изображений, конвертации файлов, инференса моделей — это правильная модель. Она масштабируется горизонтально по количеству экземпляров, а не по глубине очереди запросов.

**Размер памяти важно определить заранее.** Cloud Run завершит ваш контейнер по OOM, если он превысит настроенный лимит памяти. Оцените пиковое потребление памяти перед развёртыванием: если ваш API загружает модель объёмом 200 МБ в память, `512Mi` недостаточно — начните с `1Gi`. Увеличивайте после анализа метрик памяти Cloud Run.

## Масштабирование до нуля: компромисс холодного старта

Поведение Cloud Run по умолчанию — и его главное ценовое преимущество — это **масштабирование до нуля**: при отсутствии активных запросов все экземпляры останавливаются и вы ничего не платите.

Компромисс — **задержка холодного старта**: когда запрос поступает после периода бездействия, Cloud Run должен запустить новый контейнер, прежде чем сможет ответить. Для Python API с типичными зависимостями это занимает 2–5 секунд.

| Настройка | Поведение | Стоимость |
|---------|----------|------|
| `--min-instances 0` (по умолчанию) | Масштабирование до нуля; холодные старты после периодов бездействия | Ноль при бездействии |
| `--min-instances 1` | Один экземпляр всегда работает; холодных стартов нет | ~$10–15/месяц для 512Mi/1 vCPU |

Используйте `--min-instances 0`, когда трафик непредсказуем или нерегулярен, холодные старты приемлемы для пользователей, или вы хотите минимальные расходы на этапе разработки.

Используйте `--min-instances 1`, когда сервис ориентирован на пользователей и задержка первого запроса в 2–5 секунд заметно неприемлема, или когда у вас есть SLA по задержке.

## Переменные окружения и секреты

Cloud Run передаёт переменные окружения в контейнер при запуске через `--set-env-vars`:

```bash
gcloud run deploy my-service \
  --set-env-vars "API_KEY=abc123,DB_URL=postgres://..."
```

Для сервиса, использующего локальный файл `.env` во время разработки, скрипт развёртывания может считывать этот файл и автоматически формировать строку `--set-env-vars`:

```bash
ENV_VARS=""
while IFS= read -r line || [[ -n "$line" ]]; do
  [[ -z "$line" || "$line" == \#* ]] && continue
  key="${line%%=*}"
  val="${line#*=}"
  val="${val#\"}" val="${val%\"}"
  val="${val#\'}" val="${val%\'}"
  ENV_VARS="${ENV_VARS:+$ENV_VARS,}${key}=${val}"
done < .env

gcloud run deploy my-service --set-env-vars "$ENV_VARS" ...
```

Это позволяет хранить секреты вне репозитория, обеспечивая воспроизводимость развёртываний.

**Примечание:** Если значение содержит запятую, `--set-env-vars` молча разобьёт его на две переменные. Заключите значение в кавычки или перенесите этот секрет в [Google Secret Manager](https://cloud.google.com/secret-manager) с помощью `--set-secrets`. *(Полное руководство по Secret Manager — скоро.)*

## Публичный доступ и аутентификация

### Оговорка об org policy IAM

`--allow-unauthenticated` в скрипте развёртывания не всегда достаточен. Во многих организациях GCP действует org policy (`constraints/iam.allowedPolicyMemberTypes`), которая блокирует предоставление IAM-ролей пользователю `allUsers` — включая роль Cloud Run Invoker.

Если ваше развёртывание прошло успешно, но при вызове URL вы получаете `403 Forbidden`, причина именно в этом.

**Исправление через Cloud Console:**

1. Перейдите в **Cloud Run** → выберите ваш сервис
2. Перейдите на вкладку **Security**
3. В разделе "Authentication" выберите **Allow unauthenticated invocations**
4. Нажмите **Save**

Это устанавливает IAM policy непосредственно на ресурс сервиса, а не через команду развёртывания, и как правило обходит ограничения org policy на уровне CLI.

### Обработка аутентификации в вашем API

Большинству API — даже внутренним — необходим контроль доступа на основе ключей. Общий паттерн для публичного сервиса Cloud Run со сторонним шлюзом (например, RapidAPI):

```
Caller ──▶ Gateway ──▶ Cloud Run
           injects       validates
           X-RapidAPI-Proxy-Secret
```

| Заголовок | Кто отправляет | Что подтверждает |
|--------|-------------|----------------|
| `X-RapidAPI-Key` | Вызывающий API | Действующая подписка |
| `X-RapidAPI-Proxy-Secret` | Шлюз (внедряется) | Запрос прошёл через шлюз |
| `X-Internal-Key` | Вы (ops/тестирование) | Прямой доступ, минуя шлюз |

Ваш сервис проверяет `X-RapidAPI-Proxy-Secret`, чтобы убедиться, что запрос прошёл через шлюз. `X-Internal-Key` — это отдельный секрет для прямого доступа во время тестирования и проверок работоспособности.

**Не используйте `X-RapidAPI-Proxy-Secret` в качестве учётных данных вызывающего.** Он внедряется шлюзом, а не используется вызывающими. Обращение с ним как с ключом вызывающего — распространённая ошибка, которая либо нарушает аутентификацию, либо раскрывает серверный секрет в клиентском коде.

## Верификация после развёртывания

Каждое развёртывание должно быть верифицировано, прежде чем считаться завершённым.

**Шаг 1: проверка работоспособности** — подтверждает, что контейнер запустился и сервер слушает:

```bash
curl https://your-service-url/health
# Expected: {"status": "ok"}
```

**Шаг 2: функциональное дымовое тестирование** — подтверждает, что сервис обрабатывает запрос от начала до конца:

```bash
SECRET=$(grep INTERNAL_KEY .env | cut -d'=' -f2- | tr -d '"')

curl -X POST https://your-service-url/your-endpoint \
  -H "X-Internal-Key: $SECRET" \
  -F "file=@tests/sample.gif" \
  --output /tmp/smoke_output.png

file /tmp/smoke_output.png
```

Считывание секрета непосредственно из `.env` (а не из переменных среды оболочки) гарантирует работу теста в новой сессии терминала.

## Краткий справочник: типичные ошибки

| Симптом | Вероятная причина | Решение |
|---------|-------------|-----|
| `exec format error` в Cloud Run | Образ собран для неправильной архитектуры CPU | Добавьте `--platform linux/amd64` к `docker build` |
| Проверка работоспособности немедленно завершается ошибкой после развёртывания | Контейнер слушает неправильный хост или порт | Используйте `--host 0.0.0.0 --port 8080` в CMD |
| `docker push` возвращает `unauthorized` | Docker не аутентифицирован в Artifact Registry | Выполните `gcloud auth configure-docker us-central1-docker.pkg.dev` |
| 403 после развёртывания с `--allow-unauthenticated` | Org IAM policy блокирует `allUsers` | Установите публичный доступ через Cloud Console (вкладка Security) |
| Развёртывание успешно, но сохраняется прежнее поведение | Cloud Run кэшировал старый дайджест образа | Принудительное повторное развёртывание: `gcloud run deploy ... --image ...:latest` |
| Задержка холодного старта неприемлема | Масштабирование до нуля с большим контейнером | Установите `--min-instances 1` или уменьшите размер образа |
| `--set-env-vars` молча теряет значение | Значение содержит запятую | Заключите в кавычки или перенесите в Secret Manager |
| Контейнер завершается во время запроса | Превышен лимит памяти (OOM) | Увеличьте `--memory` (попробуйте `1Gi` или `2Gi`) |

## FAQ

**Почему в браузере появляется ошибка CORS при обращении к API?**

Есть две различные причины, которые выглядят одинаково в браузере. Во-первых, в вашем API могут не быть настроены заголовки CORS — сервер должен отвечать заголовками `Access-Control-Allow-Origin` на кросс-доменные запросы. Во-вторых, и это более распространено, API вообще не работает: когда вызов `fetch()` не может достичь сервера (сетевая ошибка, таймаут холодного старта, неправильный URL), браузер сообщает об этом как об ошибке CORS, а не как об ошибке подключения. Сначала проверьте вкладку Network в DevTools — если запрос так и не получает ответа, проблема в связи, а не в заголовках CORS.

**Как понять, это проблема CORS или API не работает?**

Вызовите эндпоинт напрямую с помощью `curl` из терминала. Если `curl` возвращает корректный ответ, сервис работает и проблема в заголовках CORS. Если `curl` тоже завершается ошибкой (соединение отклонено, таймаут, 404), сервис недоступен — сначала исправьте развёртывание, затем займитесь CORS.

**Сколько памяти следует выделить?**

Оцените пиковый объём потребления памяти: сложите базовые накладные расходы Python/фреймворка (~50–100 МБ), все модели или данные, загружаемые при запуске, и максимальный размер полезной нагрузки одного запроса. Добавьте 30% запаса и округлите до следующего уровня Cloud Run (256Mi, 512Mi, 1Gi, 2Gi, 4Gi, 8Gi). Начните с консервативного значения и наблюдайте за метриками использования памяти Cloud Run в первые несколько дней — увеличить легко, а OOM kill сразу заметен в логах.

**Я добавил `--allow-unauthenticated`, но всё равно получаю 403. Почему?**

Скорее всего, в вашей организации GCP действует IAM org policy, ограничивающая предоставление ролей пользователю `allUsers` через CLI. Флаг `--allow-unauthenticated` пытается предоставить роль Cloud Run Invoker пользователю `allUsers` во время развёртывания, что org policy блокирует. Исправьте это, перейдя в Cloud Run в Console → ваш сервис → вкладка Security → установите Authentication в "Allow unauthenticated invocations" и сохраните. Этот путь как правило обходит ограничение политики на уровне CLI.

**Моя операция API занимает более 5 минут. Могу ли я всё равно использовать Cloud Run?**

Максимальный таймаут запроса Cloud Run — 60 минут (настраивается через `--timeout`), но для операций длительностью более 5–10 минут прямой API-подход становится ненадёжным — клиенты выходят по таймауту, соединения обрываются, а повторные попытки вызывают дублирование работы. Для длительных вычислений используйте **Cloud Run Jobs**: отправьте задачу, немедленно верните job ID и позвольте клиенту опрашивать статус выполнения. Руководство по Cloud Run Jobs — скоро.

**Что происходит, когда заканчивается бесплатный уровень?**

Cloud Run и Artifact Registry автоматически переходят на оплату по факту использования — прерывания сервиса или уведомления не происходит. Биллинг Cloud Run осуществляется за запрос и за ресурс-секунду, поэтому сервис с нулевым трафиком ничего не стоит даже после исчерпания бесплатного уровня. Настройте оповещения о бюджете в консоли GCP Billing, чтобы получать уведомления до того, как расходы станут значительными.

**Могу ли я использовать порт, отличный от 8080?**

Вы можете настроить Cloud Run на использование другого порта с флагом `--port` в `gcloud run deploy`. Однако `8080` является стандартным и широко ожидаемым — меняйте его только при наличии конкретной причины. Какой бы порт вы ни настроили в Cloud Run, он должен совпадать с портом, который фактически слушает ваш контейнер.

**Как откатить неудачное развёртывание?**

Cloud Run хранит историю ревизий. В Console перейдите к вашему сервису → вкладка Revisions → выберите любую предыдущую ревизию → нажмите "Manage Traffic" и направьте 100% трафика на неё. Откаты вступают в силу в течение нескольких секунд и не требуют повторной сборки.
