## Стартовая точка: существующий API

До появления MCP, Spritesheet Forge уже имел работающий бэкенд: набор API обработки изображений, работающих на Google Cloud Platform. API выполняли основную работу — конвертировали GIF в спрайтшиты, обрезали прозрачные края, упаковывали кадры, генерировали atlas JSON.

MCP (Model Context Protocol) — открытый стандарт, позволяющий AI ассистентам вроде Claude напрямую вызывать инструменты и API через естественный язык. Что добавляет MCP — это **AI-нативный интерфейс** поверх существующего API. Вместо прямого вызова endpoints, Claude теперь может вызывать эти операции через естественный язык. Бэкенд не изменился. Изменился способ его достижения.

Это различие важно для понимания архитектуры: это не полная переделка с нуля. Это новый слой, находящийся перед тем, что уже работает.

### Почему GCP

Если вы начинаете новый проект и ещё не выбрали облачного провайдера, serverless стек GCP стоит серьёзного рассмотрения — особенно для инструментов разработчиков и утилит, где трафик непредсказуем.

Ключевое свойство — **масштабирование до нуля**. Cloud Run, управляемая контейнерная платформа GCP, полностью выключается, когда нет запросов, и запускается за несколько секунд при поступлении запроса. Вы платите только за время вычисления, которое фактически использовалось, биллируется с точностью до 100ms. Для MCP сервера, обрабатывающего спорадические вызовы инструментов, а не непрерывный трафик, это означает затраты на запуск, которые на практике практически нулевые.

Другие полезные преимущества:

- **Нет инфраструктуры для управления** — Cloud Run автоматически обрабатывает завершение HTTPS, масштабирование, проверки здоровья и откаты развёртывания
- **Любой язык, любой фреймворк** — развёртывайте любой контейнер, никакой платформо-специфичный runtime не требуется
- **Щедрый бесплатный уровень** — 2 миллиона запросов и 360,000 GB-секунд вычислений в месяц без стоимости
- **Artifact Registry + Cloud Build** — конвейер развёртывания (собрать образ → отправить → развернуть) может быть полностью автоматизирован одной командой `gcloud`

Специальный пост, охватывающий эту настройку GCP с нуля — развёртывание Cloud Run, Artifact Registry, CI/CD Cloud Build и конфигурацию IAM — скоро появится. *([Setting Up an API Service on GCP](/blog/setting-up-gcp-api-service) — coming soon)*

## Добавление слоя MCP

С уже работающим бэкендом, вопрос был в том, как его открыть для AI клиентов. Ответ был в тонком gateway на Cloudflare Workers, который говорит на языке MCP протокола и переводит запросы на существующий API.

```
MCP Client (Claude Desktop / Claude Code)
        │  Streamable HTTP (MCP protocol)
        ▼
Cloudflare Worker  ←── MCP gateway, Auth, Quota, File staging
        │  HTTP + X-MCP-Key
        ▼
GCP Cloud Run  ←── existing API (image processing, etc.)
        │
        ▼
Cloudflare R2  ←── temporary output files (1-hour TTL)
Cloudflare KV  ←── Session, Quota, OAuth state
```

### Cloudflare Worker

Worker обрабатывает всё на边缘: парсинг MCP протокола, верификацию OAuth токена, принудительное соблюдение квот на пользователя и промежуточное хранилище файлов. Workers глобально распределены без cold start — запросы приходят в ближайшую точку присутствия с sub-миллисекундными накладными расходами. Ограничение — строгий лимит времени CPU (50ms на запрос на бесплатном уровне), что делает их непригодными для всего, требующего больших вычислений. Именно поэтому тяжёлая работа остаётся на Cloud Run.

### Cloudflare R2

R2 — механизм передачи между инструментами. Каждый вывод инструмента записывается в R2 с TTL в 1 час и возвращается в виде URL. Следующий инструмент в цепи получает этот URL как вход — Worker загружает его напрямую из R2 без дополнительного HTTP круга. Это делает многошаговые рабочие процессы агента быстрыми и дешёвыми. R2 совместим с S3, поэтому любой существующий S3 SDK работает без изменений.

### Cloudflare KV

KV хранит три типа данных: токены OAuth сессии (30-дневный TTL), счётчики квот на пользователя в месяц и состояние OAuth PKCE во время потока авторизации. KV в конце концов согласуется с кэшированными на edge чтениями — хорошо подходит для этих значений, пишущихся один раз и читаемых много раз.

Для полного объяснения настройки Cloudflare Workers, конфигурирования пользовательских доменов, управления DNS и подключения R2 и KV, смотрите сопроводительное руководство: *([Complete Cloudflare Worker Setup for MCP Servers](/blog/cloudflare-worker-setup-guide) — coming soon)*

### Преимущество приватного репозитория

Разделение gateway от бэкенда решает менее очевидную проблему: **только MCP wrapper должен быть публичным**.

Код Cloudflare Worker определяет вашу API поверхность — имена инструментов, параметры, аутентификацию. Его публикация позволяет сообществу проверить интеграцию и создавать совместимые клиенты. Cloud Run бэкенд, где находится настоящая логика обработки, может оставаться в приватном репозитории. Ваши основные алгоритмы никогда не открываются.

Для коммерческого продукта это значимо: вы можете выпустить открытую MCP интеграцию, позволить сообществу способствовать слою интерфейса и полностью закрыть proprietary бэкенд. Вы демонстрируете технологию MCP без раскрытия деталей реализации.

## Что на самом деле требует полный MCP сервер

Когда Spritesheet Forge впервые запущен, MCP сервер технически работал — но Claude едва ли мог его использовать. Инструменты существовали, но серверу не хватало нескольких компонентов, на которые полагаются MCP клиенты, прежде чем они даже попытаются вызвать инструмент. Агент подключался, путался и сдавался.

Вот полный список того, что требует удалённый MCP сервер для корректной работы:

### Обработчик MCP протокола (`POST /mcp`)

Главный endpoint получает весь MCP трафик. Ему нужно обрабатывать определённую последовательность сообщений, которую каждый MCP клиент отправляет перед выполнением чего-либо полезного:

| Метод | Кто отправляет | Что это означает |
|--------|-------------|---------------|
| `initialize` | Client, первое сообщение | "Я подключаюсь, вот мои возможности" |
| `notifications/initialized` | Client, после ответа сервера на `initialize` | "Готов продолжать" |
| `tools/list` | Client, чтобы обнаружить доступные инструменты | "Что ты можешь делать?" |
| `tools/call` | Client, чтобы фактически вызвать инструмент | "Сделай это" |

Сообщения `initialize` и `notifications/initialized` должны возвращать валидный ответ даже без аутентификации — они handshake, устанавливающий сессию. Если любое из них не удаётся или возвращает ошибку auth, клиент считает соединение разорванным и останавливается.

### Определения инструментов

Каждый инструмент, зарегистрированный в `tools/list`, требует четыре вещи для завершения:

```typescript
{
  name: 'gif_to_spritesheet',
  description: '...', // instructions for the LLM — see Tool Design section
  inputSchema: {       // JSON Schema for parameters
    type: 'object',
    properties: { ... },
    required: [...]
  },
  outputSchema: { ... },  // JSON Schema for the return value
  annotations: {          // behavior hints for platforms and LLMs
    title: 'GIF to Spritesheet',
    readOnlyHint: false,
    idempotentHint: false,
    openWorldHint: true
  }
}
```

Отсутствие `outputSchema` или `annotations` не нарушает вызовы инструментов, но убивает ваш рейтинг качества на каждой платформе каталога. Более важно, что LLMs используют `outputSchema` для парсинга и рассуждения о результатах инструментов — без него модель угадывает структуру того, что возвращается.

### Endpoints обнаружения и инфраструктуры

За пределами `/mcp`, полный сервер также требует:

- **`GET /health`** — возвращает `{"status":"ok"}` с HTTP 200, без аутентификации требуется. Платформы каталога опрашивают это чтобы проверить, что ваш сервер живой.
- **`OPTIONS /mcp`** — обрабатывает CORS preflight. Требуется для любого MCP клиента на основе браузера.
- **`GET /.well-known/oauth-authorization-server`** — если используется OAuth, это то, как MCP клиенты автоматически обнаруживают ваши endpoints аутентификации. Без него клиенты подпадают под ручную конфигурацию или полностью не работают.

### Последствие отсутствия чего-либо из этого

Claude подключается к MCP серверу, запуская `initialize` → `notifications/initialized` → `tools/list` по последовательности. Если `tools/list` не удаётся (потому что требует auth, или потому что ответ неправильно сформирован), клиент не имеет определений инструментов для работы с ними. С точки зрения Claude, сервер существует но не имеет возможностей — он не может вызвать ничего.

Вот как "Agent практически неспособен использовать MCP" выглядел на практике: соединение удалось, но каждая попытка использовать инструмент не удалась, потому что шаг обнаружения никогда не завершился корректно.

### Примеры протокола

Каждое сообщение в MCP протоколе — это JSON-RPC 2.0 объект по HTTP POST. Вот как выглядит фактический обмен.

**Шаг 1 — Client отправляет `initialize`**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": { "roots": { "listChanged": true } },
    "clientInfo": { "name": "claude-code", "version": "1.0.0" }
  }
}
```

**Server отвечает своими собственными возможностями**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": { "tools": {} },
    "serverInfo": { "name": "spritesheet-forge", "version": "1.0.0" }
  }
}
```

**Шаг 2 — Client отправляет `notifications/initialized`** (ответ не требуется)

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

**Шаг 3 — Client отправляет `tools/list`** (аутентификация не требуется)

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list"
}
```

**Server возвращает все зарегистрированные инструменты**

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "gif_to_spritesheet",
        "description": "...",
        "inputSchema": { "type": "object", "properties": { "file": { "type": "string" }, "columns": { "type": "number" } }, "required": ["file"] },
        "outputSchema": { "type": "object", "properties": { "url": { "type": "string" }, "frame_width": { "type": "number" }, "frame_height": { "type": "number" }, "frame_count": { "type": "number" } } },
        "annotations": { "title": "GIF to Spritesheet", "readOnlyHint": false, "idempotentHint": true, "openWorldHint": true }
      },
      { "name": "server_info", "description": "...", "inputSchema": { "type": "object" } }
    ]
  }
}
```

Когда этот handshake завершен, клиент точно знает, какие инструменты доступны и как их вызывать. Только после этого пункта аутентификация становится релевантной — вызовы инструментов вроде `tools/call` требуют валидного Bearer токена.

**`server_info` — вызов инструмента с нулевыми аргументами**

Вот как выглядит реальный запрос `tools/call` и ответ, используя инструмент `server_info` из Spritesheet Forge:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "server_info",
    "arguments": {}
  }
}
```

**Фактический ответ:**

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": {
          "upload_url": "https://mcp.clawstudiouo.com/upload",
          "output_ttl_seconds": 3600,
          "max_file_bytes": 20971520,
          "base64_threshold_bytes": 4194304,
          "file_input_rules": {
            "small_file": "Files < 4 MB: base64-encode, prepend data URI prefix, strip all newlines.",
            "large_file": "Files ≥ 4 MB or encoded via shell: POST to /upload, use returned URL.",
            "previous_output": "Output URLs from any tool can be passed directly as input to other tools.",
            "ttl_warning": "Output URLs expire 60 minutes after creation."
          }
        }
      }
    ]
  }
}
```

`server_info` — это паттерн для следования для любого инструмента, который возвращает конфигурацию или метаданные: нулевые аргументы, детерминированный вывод, полезен для агентов для запроса до начала рабочего процесса.

## Аутентификация

### Почему аутентифицировать?

Без аутентификации, ваш MCP сервер — это открытый публичный API — кто-нибудь, кто обнаружит endpoint, может запускать ваши инструменты бесконечно, потребляя Cloud Run compute, сжигая R2 хранилище записи и исчерпывая квоту, которая принадлежит реальным пользователям. Аутентификация решает три проблемы сразу:

- **Защита ресурсов**: каждый вызов инструмента переводится непосредственно в стоимость compute. Без знания кто звонит, вы не можете принудительно выполнить лимиты.
- **Управление квотой**: квоты на пользователя в месяц требуют стабильной идентичности для отслеживания. Без идентичности нет справедливого применения.
- **Профилактика злоупотребления**: публичный endpoint без auth тривиально скрипируется — один плохой актёр может спровоцировать ваши счета или деградировать сервис для всех.

### Опции аутентификации

| Метод | Опыт пользователя | Реализация | Поддержка MCP клиента |
|--------|----------------|----------------|-------------------|
| Без auth | Фрикционно | Тривиально | Универсально |
| Статический API ключ | Плохо — пользователь должен копировать-вставлять в конфиг | Просто | Универсально |
| OAuth 2.1 + PKCE | Гладко — один клик браузера | Умеренно | Claude Desktop, Claude Code |

**Без auth** подходит только для локальных или только внутренних серверов, где сетевая граница — это граница безопасности. Для публичного удалённого сервера, это означает, что кто-нибудь в интернете может вызывать ваши инструменты.

**API ключи** — это очевидный первый выбор: генерируйте ключ, дайте его пользователю, готово. Проблема в опыте распределения. Пользователь должен найти dashboard или страницу docs, скопировать случайную строку, открыть свой конфиг файл, вставить её и перезапустить клиент. Это многошаговый процесс с множеством точек отказа, и нет восстановления если они его потеряют. Каждый новый MCP клиент требует той же ручной настройки.

**OAuth 2.1 + PKCE** — это более много работы чтобы реализовать но дает драматически лучший опыт. MCP клиент обрабатывает весь поток нативно — он автоматически открывает браузер когда требуется токен. Пользователь видит страницу логина GitHub, кликает "Authorize", и клиент хранит полученный токен внутри. С точки зрения пользователя, это один клик без конфиг файла.

### Как Spritesheet Forge это реализует

Реализация использует GitHub как поставщика идентичности, Cloudflare KV для хранилища токена и стандартный OAuth 2.1 + PKCE поток:

**1. Автообнаружение через `/.well-known/oauth-authorization-server`**

MCP клиенты читают этот endpoint перед инициированием любого OAuth потока. Он возвращает точку авторизации, точку токена и поддерживаемые типы грантов. Без него, клиенты требуют ручной конфигурации или полностью не подключаются.

**2. Динамическая регистрация клиента (RFC 7591)**

Любой MCP клиент может зарегистрировать себя программно, POSTя в endpoint регистрации. Это означает, что новые клиенты могут подключаться без предварительного утверждения или листинга где-либо — сервер обрабатывает регистрацию автоматически.

**3. PKCE поток**

Предотвращает перехват кода авторизации. Клиент генерирует случайный `code_verifier`, отправляет его хеш (`code_challenge`) с запросом авторизации, затем доказывает что держит оригинальный verifier при обмене кода на токен. Это закрывает вектор атаки где код авторизации мог бы быть украден в пути.

**4. Хранилище сессии KV**

Токен сессии хранится в Cloudflare KV под `session:{userId}` с 30-дневным TTL. Каждый запрос `tools/call` валидирует Bearer токен против KV перед тем как запрос достигает Cloud Run.

**5. Fallback скрипта**

Для пользователей, работающих в скриптах, CI конвейерах или бенчмарк окружениях, где браузер OAuth не практичен, доступен скрипт `get-token.py` для скачивания. Он запускает полный OAuth поток в терминале, выводит полученный токен и сохраняет его в `~/.spritesheet-forge-token`.

### Заголовок X-MCP-Key: аутентификация внутреннего сервиса

Архитектура имеет два слоя: Cloudflare Worker (публичный gateway) и Cloud Run (приватный бэкенд). Cloud Run работает по URL, который технически досягаем из интернета — кто-нибудь, кто его обнаружит, мог бы POST запросы напрямую, обходя Worker полностью. Это означает обход OAuth верификации, принудительного выполнения квот и rate limiting.

Заголовок `X-MCP-Key` закрывает этот пробел. Это разделённый секрет известный только Worker и Cloud Run. Worker валидирует каждый входящий OAuth токен, затем перенаправляет запрос к Cloud Run с этим заголовком приложенным. Cloud Run отклоняет любой запрос, который не включает правильный ключ.

```
User → Worker:     Authorization: Bearer <oauth-token>   (public auth)
Worker → Cloud Run: X-MCP-Key: <internal-secret>         (internal auth)
```

Это **защита в глубину**: даже если Cloud Run URL утечёт через логи, сообщения об ошибке или обратный инженеринг, атакующий не может вызвать его без внутреннего ключа. Весь трафик принудительно идёт через gateway, и вся безопасность enforcement сохранена.

Без этого, "приватный бэкенд" было бы ложное утверждение — бэкенд был бы по-прежнему эффективно публичен для кого-нибудь, кто достаточно захочет.

## Дизайн вввода файла

Этот раздел специфичен для MCP серверов, инструменты которых обрабатывают файлы — конвертеры изображений, парсеры документов, аудио процессоры и подобные. Если ваши инструменты обрабатывают только текст или структурированные данные, вы не столкнётесь с этой проблемой. Но для файло-интенсивных API, это одна из самых практически ограничивающих проблем, которую вы встретите.

Основная проблема состоит в том, что передача файлов в Agent сложнее, чем выглядит. Интуитивный подход — base64-кодировать файл и отправить inline — теоретически работает но попадает на жёсткое ограничение на практике: **Claude Code's shell инструмент имеет ~256 KB контекст лимит на stdout вывод**. Base64 кодирование расширяет размер файла на ~33%, что означает реальный безопасный потолок для inline base64 вокруг 185 KB. Большинство изображений, аудио файлы и документы больше чем это.

Это делает base64 непрактичным для большинства реальных use cases обработки файлов. Решение, которое мы добавили, было специальным `/upload` endpoint на слое MCP — вне самого MCP протокола. Пользователь (или Agent) POSTs файл туда напрямую, получает обратно URL и передаёт этот URL инструменту вместо вставления файла inline. Worker затем загружает файл на стороне сервера из R2, обходя ограничение размера контекста полностью.

**Почему Cloudflare R2 для хранилища файлов?**

R2 — это S3-совместимое хранилище объектов Cloudflare, и это правильный выбор здесь по одной конкретной причине: **нулевые сборы за исходящий трафик**. AWS S3 и большинство других сервисов хранилища объектов берут за передачу данных — каждый раз когда результат инструмента читается (что происходит при каждом связанном вызове инструмента), вы платите. R2 ничего не берёт за исходящий трафик. Для MCP сервера, который перемещает файлы между инструментами часто, это имеет значение.

Бесплатный уровень R2 также достаточно щедрый чтобы MCP сервер с низким-к-умеренному трафику мог работать полностью в его пределах:

| Ресурс | Бесплатный уровень |
|----------|-----------|
| Хранилище | 10 GB/месяц |
| Class A операции (записи, удаления) | 1 миллион/месяц |
| Class B операции (чтения) | 10 миллионов/месяц |
| Исходящий трафик (передача данных) | Бесплатно, всегда |

Результаты инструментов хранятся с 1-часовым TTL и удаляются автоматически — так что использование хранилища остаётся низким даже при активном использовании. Файл обработанный и отброшенный в течение часа никогда не считается к месячному total хранилища каким-нибудь значимым способом.

MCP инструменты, принимающие файлы, должны обрабатывать три отличных сценария ввода:

| Сценарий | Метод |
|----------|--------|
| Маленькие файлы (< ~185 KB) | base64 data URI: `data:image/png;base64,...` |
| Большие файлы или файлы из shell | POST к `/upload` endpoint, передать обратно URL |
| Вывод из предыдущего инструмента | Передать URL вывода напрямую — Worker загружает из R2 |

Неочевидное ограничение: Claude Code's shell инструмент имеет ~256 KB контекст лимит на stdout. Base64 кодирование расширяет размер файла на ~33%, поэтому практический потолок для inline base64 вокруг 185 KB, не 4 MB. Ваши описания инструментов должны явно заявлять это ограничение и указывать пользователей к upload endpoint когда это имеет значение.

**Ошибка base64 newline.** Shell инструменты вроде `openssl base64` и CLI `base64` вставляют newline каждые 76 символов. Передача этой строки напрямую как data URI вызывает `INVALID_BASE64` ошибки на сервере. Поставьте это предупреждение в описание вашего инструмента:

> "Strip all whitespace and newlines from the base64 string before prepending the data URI prefix. Example: `base64 file.png | tr -d '\n'`"

## Дизайн инструмента, который работает с LLMs

### Шаг 0: подключите Claude к вашему MCP серверу

Перед тем как любой инструмент может быть использован, Claude должен быть подключен к MCP серверу. Это звучит очевидно, но стоит объяснить: Claude не автоматически обнаруживает или подключается к MCP серверам. Вы явно конфигурируете соединение и до того как вы это делаете, Claude не знает, что сервер существует.

**Claude Desktop** — добавьте к `claude_desktop_config.json` (найдите его через Settings → Developer):

```json
{
  "mcpServers": {
    "spritesheet-forge": {
      "type": "http",
      "url": "https://mcp.clawstudiouo.com/mcp"
    }
  }
}
```

**Claude Code CLI** — добавьте через терминал:

```bash
claude mcp add spritesheet-forge --transport http https://mcp.clawstudiouo.com/mcp
```

Если сервер не конфигурирован, Claude не скажет "Я не могу найти этот инструмент." Он просто будет действовать как если бы инструмент не существует — ища в сети альтернативы, галлюцинируя похожие-звучащие инструменты, которых он не имеет на самом деле, или производя обобщённый ответ, который полностью упускает то, что вы просили. Мода отказа молчаливая и запутанная.

### Как пользователи находят ваш MCP сервер

Подключение Claude — первый шаг. Информирование пользователей о существовании сервера в первую очередь — это отдельная проблема. Есть несколько каналов, каждый достигающий другую аудиторию:

**Исходный код и документация**
- [GitHub repository](https://github.com/LAXY9887/Game-Dev.-Spritesheet-Forge) — основной источник правды. Разработчики смотрят сюда первыми. Ясный README с endpoint URL и фрагмент конфига — это минимум.
- [Dedicated tutorial page](https://sprite-forge-mcp.tutorial.clawstudiouo.com) — автономная страница, которая проходит через установку, аутентификацию и примеры подсказок. Полезна для не-разработчиков, которые не хотят читать README.

**Официальные реестры**
- [Anthropic MCP Registry](https://registry.modelcontextprotocol.io/?q=io.github.LAXY9887%2Fspritesheet-forge) — официальный индекс Anthropic MCP серверов. Это место, где MCP приложения клиентов запрашивают чтобы показывать курирующие списки серверов в приложении.

**Маркетплейсы и директории**
- [Smithery.ai](https://smithery.ai/servers/lxya98874322688423/spritesheet-forge) — интегрирован напрямую в MCP браузер Claude Code. Пользователи могут находить и устанавливать серверы без выхода из CLI.
- [MCP Marketplace](https://mcp-marketplace.io/server/game-dev-spritesheet-forge) — специализированный маркетплейс с моделью разделения доходов для платных уровней.
- GitHub Marketplace — доступен для экосистемы разработчиков GitHub.

Каналы усиливают друг друга. Пользователь, который находит сервер на Smithery, часто проверяет GitHub репо далее. Страница tutorial преобразует обнаружение в фактическую установку. Покрытие всех из них стоит мало чтобы поддерживать и достигает аудиторий, которые не перекрываются.

### Написание описаний инструментов, которые на самом деле работают

Описания инструментов — это не документация для людей — это инструкции LLMs используют чтобы решить *когда* и *как* вызвать ваш инструмент. Плохо написанное описание результирует в модели вызывающей неправильный инструмент, передающей неправильные параметры или производящей ошибки, которые трудно отлаживать.

Что включает хорошее описание инструмента:

- **Формат ввода**: URL? data URI? Какие MIME типы принимаются?
- **Вывод**: что возвращает инструмент? URL? JSON структура? Какой TTL?
- **Ограничения**: ограничение размера файла, взаимодействия параметров, известные gotchas
- **Примеры**: для сложных правил ввода, дайте inline пример или shell команду

**Дизайн для цепления.** Сделайте каждый вывод инструмента напрямую используемым как ввод другого инструмента. Это позволяет агентам компоновать многошаговые рабочие процессы естественно:

```
gif_to_spritesheet → split_spritesheet → frames_to_animation
```

**Добавьте инструмент `server_info`.** Предоставьте инструмент с нулевыми аргументами, который возвращает runtime конфигурацию: URL endpoint загрузки, TTL выходного файла, ограничение размера файла и правило для выбора между base64 и загрузкой. Это предотвращает эту информацию от становления затхлой по отдельным описаниям инструментов и даёт агентам надёжный способ запросить её перед началом сложных рабочих процессов.

## Краткая справка ошибок

| Симптом | Корневая причина | Исправление |
|---------|-----------|-----|
| Платформа показывает "0 tools found" | `tools/list` требует auth | Добавьте `initialize`, `notifications/initialized`, `tools/list` к handshake whitelist |
| Smithery Quality Score равен 0 | Отсутствует `outputSchema` / `annotations` | Добавьте оба поля ко всем инструментам |
| Ошибка декодирования `INVALID_BASE64` | Shell инструменты вставляют newlines в base64 | Предупредите в описании инструмента; используйте `tr -d '\n'` |
| Agent говорит "у меня нет этого инструмента" и начинает поиск в сети | MCP сервер не конфигурирован в клиенте | Добавьте конфиг сервера к `claude_desktop_config.json`, или запустите `claude mcp add` |
| Страница авторизации OAuth никогда не открывается | `/.well-known/oauth-authorization-server` не общедоступен | Убедитесь endpoint достижим без auth |
| Upload endpoint возвращает `401` | Bearer токен отсутствует или истёк | Пользователь переаутентифицируется; запустите `get-token.py` если нужно |
| URL вывода инструмента возвращает 404 или не работает | Истёк TTL объекта R2 (60 минут) | Повторно запустите исходящий инструмент чтобы получить свежий URL |
| Cloud Run возвращает `403` на все запросы | Заголовок `X-MCP-Key` отсутствует или неправилен | Проверьте секрет в переменных окружения Worker |
| MCP клиент на основе браузера не может подключиться | Отсутствуют CORS заголовки на `/mcp` | Добавьте `OPTIONS` preflight обработчик + `Access-Control-Allow-Origin: *` ко всем ответам |

## Часто задаваемые вопросы

**Что такое удалённый MCP сервер?**

Удалённый MCP сервер — это облачный сервис, который реализует Model Context Protocol, позволяя AI ассистентам вроде Claude вызывать инструменты по интернету через естественный язык. В отличие от локальных MCP серверов — которые работают на машине пользователя и доступны только с той машины — удалённый сервер доступен любому аутентифицированному MCP клиенту где угодно, без локальной установки.

**Как я добавляю MCP сервер в Claude Desktop или Claude Code?**

Для Claude Desktop, добавьте конфиг сервера к `claude_desktop_config.json` (найдите его под Settings → Developer). Для Claude Code, запустите `claude mcp add <name> --transport http <url>` в терминале. До тех пор пока соединение явно не конфигурировано, Claude не имеет знания что сервер существует и не может использовать любые из его инструментов.

**Бесплатно ли запускать удалённый MCP сервер на Cloudflare и GCP?**

Да, для низко-к-умеренному трафику. Cloudflare Workers включает 100,000 запросов в день на бесплатном уровне. Cloudflare R2 предлагает 10 GB хранилища, 1 миллион записей и 10 миллионов чтений в месяц без стоимости — с нулевыми сборами за исходящий трафик. GCP Cloud Run предоставляет 2 миллиона запросов и 360,000 GB-секунд вычислений в месяц бесплатно. Инструмент разработчика обрабатывающий спорадические вызовы инструментов может работать полностью в этих лимитах.

**Почему использовать OAuth вместо API ключей для MCP аутентификации?**

OAuth 2.1 предоставляет лучший пользовательский опыт. С API ключами, пользователи должны вручную копировать-вставлять токен в конфиг файл — многошаговый процесс без само-обслуживающегося восстановления если ключ потерян. С OAuth, Claude Desktop и Claude Code обрабатывают поток нативно: они открывают браузер, пользователь кликает "Authorize", и токен хранится автоматически. Пользователь никогда не трогает конфиг файл.

**Почему Claude не может найти мой MCP инструмент?**

Наиболее частая причина состоит в том, что MCP сервер не конфигурирован в клиенте. Claude не обнаруживает серверы автоматически. Если сервер конфигурирован но инструменты всё ещё не появляются, проверьте что `tools/list` доступен без аутентификации — если это требует Bearer токена, Claude не может получить список инструментов во время начального handshake и будет вести себя как если бы сервер не имел инструментов.

**Как я передаю большие файлы в MCP инструмент?**

Для файлов больше чем ~185 KB, используйте endpoint `/upload` сервера вместо base64 кодирования. POST файл напрямую (multipart/form-data), получите URL в ответе и передайте этот URL как параметр файла инструмента. Сервер загружает файл на стороне сервера, обходя ~256 KB лимит вывода shell Claude Code, который делает inline base64 непрактичным для большинства реальных файлов.

**Что такое заголовок X-MCP-Key?**

X-MCP-Key — это разделённый секрет используемый для аутентификации запросов между Cloudflare Worker (публичный gateway) и GCP Cloud Run бэкендом. Это гарантирует что весь трафик достигает Cloud Run только через Worker — не напрямую из интернета. Без него, кто-нибудь, кто обнаружит Cloud Run URL, мог бы обойти OAuth верификацию и enforcement квот полностью.

**Должен ли я делать мой код бэкенда публичным чтобы запустить MCP сервер?**

Нет. Только MCP wrapper (Cloudflare Worker) должен быть публичным репозиторием — он определяет вашу API поверхность и позволяет сообществу проверить интеграцию. Cloud Run бэкенд, где находится настоящая бизнес-логика, может оставаться приватным. Это позволяет вам публиковать открытую MCP интеграцию пока сохраняя proprietary алгоритмы и детали реализации в приватном репозитории.
